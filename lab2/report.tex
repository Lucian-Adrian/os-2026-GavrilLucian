\begin{utmabstract}[Abstract]
This report covers building and booting MIT xv6 on RISC-V under QEMU, exploring its shell and source tree, and adding two user programs. The required utility, \texttt{user/sleep.c}, checks its argument count, converts the tick count with \texttt{atoi()}, and calls the kernel \texttt{sleep()} system call. The optional \texttt{pingpong.c} program exchanges a single byte between parent and child processes over two unidirectional pipes. Build and boot timings, shell checks, and source inspection show how user programs cross into the kernel through system calls and how the shell wires pipelines.
\utmkeywords{operating systems, xv6, riscv, system calls, qemu, process scheduling, pipelines}
\end{utmabstract}

\utmintroduction
Production kernels like Linux contain millions of lines of code, which makes it hard to trace a full mechanism from user space down to hardware. MIT xv6 is a Unix Version 6 re-implementation written in roughly 9,000 lines of C for 64-bit RISC-V, small enough to read end to end.

The goal of Laboratory 2 is to build xv6 from source, boot it under QEMU, inspect the boundary between \texttt{user/} and \texttt{kernel/} code, and add a small user program:
\begin{utmenumerate}
\item \textbf{Build and boot}: compiling the RISC-V kernel, building \texttt{fs.img} with \texttt{mkfs}, and booting to the xv6 shell prompt;
\item \textbf{Shell checks}: running basic utilities (\texttt{ls}, \texttt{cat}, \texttt{echo}, \texttt{wc}) and a pipeline (\texttt{ls | grep c});
\item \textbf{Source reading}: tracing user-space stubs, \texttt{ecall} traps, the system-call dispatch table, and kernel handlers;
\item \textbf{User programs}: writing \texttt{user/sleep.c} and the optional two-pipe \texttt{pingpong.c} exercise, then registering them in \texttt{UPROGS}.
\end{utmenumerate}

\chapter{Compilation, Booting, and Shell Operations}

\section{Build and Boot Sequence}
The kernel and user programs were built with the RISC-V cross-compiler, and \texttt{mkfs} created \texttt{fs.img}. The build took 2.158 seconds. QEMU 8.2.2 booted the kernel and reached the shell prompt in 2.459 seconds:

\begin{verbatim}
$ make -C xv6-riscv -j2 kernel/kernel fs.img
Build elapsed seconds: 2.158

$ qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel \
  -m 128M -smp 3 -nographic -drive file=fs.img,if=none,format=raw,id=x0 \
  -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0

xv6 kernel is booting
hart 1 starting
hart 2 starting
init: starting sh
$
\end{verbatim}

The line \texttt{init: starting sh} shows that kernel initialization finished and PID 1 (\texttt{init}) launched the first interactive shell in user space.

\section{Answers to Observe Questions (Part 2: xv6 Shell)}
\begin{utmenumerate}
\item \textbf{Included programs}: three programs built into \texttt{fs.img} via \texttt{UPROGS} are \texttt{ls}, \texttt{cat}, and \texttt{echo};
\item \textbf{Why a pipeline needs two processes}: in \texttt{ls | grep c}, \texttt{ls} and \texttt{grep} are separate executables that each need their own address space and file descriptors. In \texttt{user/sh.c}, the shell creates a kernel pipe with \texttt{pipe()}, forks two children, redirects stdout of \texttt{ls} and stdin of \texttt{grep} using \texttt{close()} and \texttt{dup()}, and lets the kernel pass bytes through the pipe buffer;
\item \textbf{Comparison with the Linux shell}: the xv6 shell handles basic commands, pipes, redirection, sequences (\texttt{;}), and background execution (\texttt{\&}), but it has no globbing, environment variables, quoting, \texttt{PATH} lookup, or command history. Bash on Linux provides full POSIX expansions, job control, and scripting.
\end{utmenumerate}

\chapter{Source Code Inspection: User vs. Kernel Boundary}

\section{System Calls in user/cat.c}
Reading \texttt{user/cat.c} shows which operations cross into the kernel:
\begin{itemize}
\item \texttt{open(argv[i], O\_RDONLY)}: asks the kernel to open a file and return a descriptor;
\item \texttt{read(fd, buf, sizeof(buf))}: reads bytes from the file into a user buffer;
\item \texttt{write(1, buf, n)}: writes bytes to standard output (fd 1);
\item \texttt{close(fd)}: releases the file descriptor;
\item \texttt{exit(0)}: ends the process and passes its exit status to the parent.
\end{itemize}
\texttt{fprintf} is a user-space formatting function in \texttt{user/printf.c}, not a system call; it formats characters and calls \texttt{write()} underneath.

\section{Answers to Observe Questions (Part 3: Reading Source)}
\begin{utmenumerate}
\item \textbf{System calls in cat.c}: \texttt{open}, \texttt{read}, \texttt{write}, \texttt{close}, and \texttt{exit}. \texttt{fprintf} is a user-space library function;
\item \textbf{Location of sys\_read}: \texttt{kernel/sysfile.c}, line 69;
\item \textbf{User vs. kernel code}: code in \texttt{kernel/} runs in RISC-V supervisor mode with direct access to physical memory, page tables, and devices. Code in \texttt{user/} runs in unprivileged user mode and must request hardware or OS services through system calls.
\end{utmenumerate}

\chapter{User Utilities: sleep and pingpong}

\section{Implementation of user/sleep.c}
The \texttt{sleep} program expects one integer argument (ticks):
\begin{verbatim}
#include "kernel/types.h"
#include "user/user.h"

int
main(int argc, char *argv[])
{
  if (argc != 2) {
    fprintf(2, "usage: sleep <ticks>\n");
    exit(1);
  }
  sleep(atoi(argv[1]));
  exit(0);
}
\end{verbatim}

The pinned xv6 revision provides the kernel tick delay through \texttt{sleep(int)}.

\section{Build Registration and Verification}
Adding \texttt{\$U/\_sleep\textbackslash} to \texttt{UPROGS} in the \texttt{Makefile} compiles the program and packs it into \texttt{fs.img}. Under QEMU, both the normal and error paths worked as expected:
\begin{verbatim}
$ sleep 10
# Returns to the prompt after 0.958 s

$ sleep
usage: sleep <ticks>
\end{verbatim}

\section{Optional Two-Pipe Exercise: pingpong.c}
To pass a byte from parent to child and back without the two processes racing on a single pipe, \texttt{pingpong.c} creates two pipes before calling \texttt{fork()}:
\begin{verbatim}
$ pingpong
4: received ping
3: received pong
\end{verbatim}

The parent writes one byte to \texttt{parent\_to\_child[1]}, the child (PID 4) reads it, prints its PID, and writes the byte back on \texttt{child\_to\_parent[1]}. The parent (PID 3) reads the reply, prints its PID, and calls \texttt{wait()}. Closing the unused ends of both pipes ensures clean EOF handling and prevents leaked descriptors.

\utmconclusions
Building and extending xv6 made the structure of a small Unix kernel concrete:
\begin{utmenumerate}
\item User programs are isolated from hardware and reach kernel services only through system-call stubs (\texttt{usys.S}) and the trap dispatcher (\texttt{syscall.c});
\item Blocking inside \texttt{sys\_sleep} lets the scheduler run other work while waiting for timer ticks instead of burning CPU in a user loop;
\item Pipelines work by connecting separate processes through kernel pipe buffers and redirecting standard input and output;
\item Adding a new command to xv6 only requires a user C file and an entry in \texttt{UPROGS} so \texttt{mkfs} includes it in \texttt{fs.img}.
\end{utmenumerate}
