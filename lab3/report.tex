\utmintroduction
\textbf{Purpose of the work.} To work fluently in Bash, to predict what the shell does to a command line before it runs, to send output and errors exactly where they are wanted, and to answer real questions about a data set with one line of small filters joined by pipes. The last part turns the best one-liners into a script with argument checking and runs it automatically with cron.

\textbf{Environment.} Debian GNU/Linux 13 (trixie), GNU Bash 5.2.37, GNU coreutils 9.7, user \texttt{dev1}, working directory \texttt{\~{}/os-lab3}. The data set \texttt{access.log} was generated with the exact block from the handout; \texttt{wc -l access.log} printed \texttt{500 access.log}. Every terminal figure is the real output of the command shown in it.

\textbf{Method.} For every command marked PREDICT the prediction was written down first and then compared with the real output (Table~\ref{tab:predictions}). Every answer to an \emph{Observe} question is backed by a figure.

\section{Tab completion and history search}
\texttt{ls /usr/sh} has a single match, so the first Tab already completes it in place to \texttt{/usr/share/}; the second Tab has nothing left to list. With a shorter, ambiguous prefix (\texttt{/usr/s}) the double Tab lists every candidate: \texttt{sbin/ share/ src/}. \texttt{cd /et} plus one Tab completes to \texttt{cd /etc/}, including the trailing slash, because \texttt{/etc} is the only match. After running \texttt{date}, \texttt{whoami} and \texttt{uname -r}, \texttt{Ctrl+R} followed by \texttt{da} found \texttt{date} in the history, and Enter executed it again (Figure~1.1).

\section{Answers to the Observe questions}
\begin{utmenumerate}
\item \textbf{Which of cd, ls, echo are built-ins, and why MUST cd be one?} \texttt{cd} and \texttt{echo} are shell built-ins; \texttt{ls} is an external program, \texttt{/usr/bin/ls} (Figure~1.2). The current directory is a property of each process. An external \texttt{cd} would run in a child process created with \texttt{fork()}, change the directory of that child with \texttt{chdir()}, and exit; the shell itself would stay where it was. Only the shell process can change its own directory, so \texttt{cd} must run inside it.
\item \textbf{How many directories are in your PATH, and in which one is ls?} 4 directories: \texttt{/usr/local/bin}, \texttt{/usr/bin}, \texttt{/bin}, \texttt{/usr/games} (Figure~1.3). \texttt{ls} is in \texttt{/usr/bin}; it is found there first because the directories are searched left to right.
\item \textbf{What exit code does a command that is not found return?} \texttt{127} (Figure~1.4). For comparison, a file that exists but is not executable gives \texttt{126} (Figure~5.2).
\item \textbf{Which option of ls sorts by modification time?} \texttt{-t}, ``sort by time, newest first'' (Figure~1.4); \texttt{ls -lt} shows the times and \texttt{ls -ltr} puts the newest file last.
\end{utmenumerate}

\section{Answers to the Observe questions}
\begin{utmenumerate}
\item \textbf{Prediction against output.} See Table~\ref{tab:predictions}: 7 of 10 lines matched exactly; the three differences are explained in the table.
\item \textbf{echo knows nothing about files, yet echo *.c printed file names. Who produced them?} The shell. During pathname expansion Bash reads the directory, sorts the names that match \texttt{*.c}, and replaces the pattern with them, so \texttt{echo} is started with \texttt{argv = \{"echo", "a.c", "b.c"\}} and simply prints its arguments. \texttt{echo "*.c"} prints \texttt{*.c} because quotes switch globbing off (Figure~2.4).
\item \textbf{Why did ls alfa beta.txt fail? Give two different ways to fix it.} The unquoted space splits the line into two words, so \texttt{ls} looks for two files, \texttt{alfa} and \texttt{beta.txt}, and neither exists. Fixes (Figure~2.3): quote the name, \texttt{ls "alfa beta.txt"} (or \texttt{'alfa beta.txt'}), or escape the space, \texttt{ls alfa\textbackslash\ beta.txt}. Tab completion produces the escaped form automatically.
\item \textbf{What is the difference between single and double quotes?} Inside single quotes nothing is expanded: \texttt{'\$HOME'} and \texttt{'\$(whoami)'} stay literal. Inside double quotes \texttt{\$} expansions and command substitution still work (\texttt{"\$HOME"} becomes \texttt{/home/dev1}), but word splitting and globbing do not. A backslash quotes a single character (Figure~2.4).
\item \textbf{Why does ls show 'alfa beta.txt' in quotes?} Since coreutils 8.25, \texttt{ls} uses \texttt{--quoting-style=shell-escape} by default when it writes to a terminal. It quotes names with spaces or special characters, so the printed name can be copied back into a command as one argument. With \texttt{--quoting-style=literal} the quotes disappear (Figure~2.3).
\end{utmenumerate}

\section{Answers to the Observe questions}
\begin{utmenumerate}
\item \textbf{Which file got the error message, and which got the listing?} \texttt{out.txt} got the listing of \texttt{/etc} (stdout, file descriptor 1); \texttt{err.txt} got the one line \texttt{ls: cannot access '/nope': No such file or directory} (stderr, file descriptor 2), as Figure~3.1 shows.
\item \textbf{What is the difference between > all.txt 2>\&1 and 2>\&1 > all.txt?} Redirections are applied left to right, and \texttt{2>\&1} means ``make fd 2 a copy of fd 1 \emph{as it is now}''. In \texttt{> all.txt 2>\&1}, fd 1 is first pointed at the file, then fd 2 copies it, so both streams go to \texttt{all.txt}: \texttt{grep -c nope all.txt} prints \texttt{1}. In \texttt{2>\&1 > all.txt}, fd 2 copies fd 1 while fd 1 is still the terminal, and only afterwards is fd 1 moved to the file. The error therefore appears on the screen and the file contains only the listing (\texttt{grep -c} prints \texttt{0}), as Figure~3.2 shows.
\item \textbf{Why does wc -l < access.log print only a number?} With \texttt{<} the shell opens the file and connects it to fd 0 before \texttt{wc} starts; \texttt{wc} reads anonymous standard input and never learns a file name. With \texttt{wc -l access.log}, \texttt{wc} opens the file itself and prints the name it was given: \texttt{500} against \texttt{500 access.log} (Figure~3.1).
\item \textbf{Explain ; \&\& ||.} \texttt{;} runs the next command unconditionally; \texttt{\&\&} runs it only if the previous command succeeded (exit status 0); \texttt{||} runs it only if the previous command failed (non-zero status). In Figure~3.3, \texttt{ls /nope || echo} printed \texttt{failed with code 2}, while the text after \texttt{\&\&} was never printed.
\end{utmenumerate}
In Figure~3.4, \texttt{sleep 100 \&} starts the job in the background, so the prompt returns immediately. \texttt{jobs} shows it as \texttt{Running}; \texttt{kill \%1} sends it SIGTERM, and the next \texttt{jobs} reports it as \texttt{Terminated} once and then no longer lists it.

\chapter{Answering questions with one-liners}
Each line of \texttt{access.log} has five space-separated fields: date, time, user, result, page. All answers are in \texttt{oneliners.sh}, one line per question, and the file runs with \texttt{bash oneliners.sh} inside \texttt{\~{}/os-lab3} (Figure~4.9). Both self-checks from the handout pass: the Q3 counts add up to 500, and the per-user failure counts add up to the Q1 total of 100.

\section{Q1. How many requests failed?}
\texttt{grep -c FAIL access.log} gives \textbf{100}. This is consistent with the generator: a line is FAIL when $i \bmod 5 = 0$, and $500/5 = 100$.
\shot{fig4_1.png}{Number of failed requests}

\section{Q2. How many different pages, and which?}
\texttt{cut -d' ' -f5 access.log | sort -u | awk '\{print\} END\{print NR " different pages"\}'} gives \textbf{4 pages}: \texttt{/page0}, \texttt{/page1}, \texttt{/page2}, \texttt{/page3}.
\shot{fig4_2.png}{Different pages requested}

\section{Q3. How many requests did each page get?}
\texttt{cut -d' ' -f5 access.log | sort | uniq -c} gives \textbf{125} for each page, $4 \times 125 = 500$. The second command in Figure~4.3 checks that the sum is 500.
\shot{fig4_3.png}{Requests per page and the check that they add up to 500}

\section{Q4. Which user or users have the most failed requests?}
\texttt{grep FAIL access.log | cut -d' ' -f3 | sort | uniq -c | sort -rn | awk 'NR==1\{max=\$1\} \$1==max'} prints every user tied at the maximum, not a fixed number of lines: \textbf{user3 and user5, 15 failures each}. The other five users have 14 each, and the sum over users is $2\cdot15+5\cdot14=100$, equal to Q1.
\shot{fig4_4.png}{Users with the most failed requests and the check against Q1}

\section{Q5. How many requests did user3 make, and how many failed?}
\texttt{grep -w} matches \texttt{user3} as a whole word: \textbf{72 requests, 15 failed}. As a cross-check, user3 is $i \equiv 3 \pmod 7$, which gives 72 values in 1..500. A request fails for $i \equiv 0 \pmod 5$ as well, i.e.\ $i \equiv 10 \pmod{35}$, which gives 15 values.
\shot{fig4_5.png}{Requests and failures of user3}

\section{Q6. The last 3 failed requests, time and user only}
\texttt{grep FAIL access.log | tail -n 3 | cut -d' ' -f2,3} gives \texttt{10:10 user0}, \texttt{10:15 user5}, \texttt{10:20 user3} (lines 490, 495 and 500).
\shot{fig4_6.png}{The last three failed requests}

\section{Q7. Login shells in /etc/passwd}
\texttt{cut -d: -f7 /etc/passwd | sort | uniq -c | sort -rn} gives 29 accounts with \texttt{/usr/sbin/nologin}, 3 with \texttt{/bin/false}, 3 with \texttt{/bin/bash} and 1 with \texttt{/bin/sync}. Most accounts are system services that must never log in interactively.
\shot{fig4_7.png}{Accounts per login shell}

\section{Q8. Why do ls /etc | wc -l and ls -l /etc | wc -l differ by one?}
\textbf{Prediction:} the long format adds one header line. \textbf{Result:} 210 against 211, and the extra line is \texttt{total 1064}, the number of 1~KiB blocks used by the listed entries. Every other line is one entry in both formats, so the difference is always exactly one.
\shot{fig4_8.png}{Line counts with and without -l}

\section{Bonus: minute ending in 0 and failed}
\texttt{grep -E '\^{}[\^{} ]+ 10:[0-5]0 [\^{} ]+ FAIL ' access.log} anchors the time to the second field and the result to the fourth, so a \texttt{0} in another field cannot match. It prints \textbf{50 lines}. This agrees with arithmetic: the minute is $i \bmod 60$, so it ends in 0 exactly when $i \equiv 0 \pmod{10}$, and every such $i$ is also divisible by 5, hence FAIL. There are $500/10 = 50$ such lines.

\section{Answers to the Observe questions}
\begin{utmenumerate}
\item \textbf{What does \#!/bin/bash do, and what happens before chmod +x?} The shebang tells the kernel, inside \texttt{execve()}, which interpreter runs the file: the kernel actually executes \texttt{/bin/bash ./report.sh access.log}. Without the execute bit the kernel refuses: \texttt{Permission denied}, exit code \texttt{126} (Figure~5.2). \texttt{bash report.sh} would still work, because then bash only reads the file.
\item \textbf{Why ./report.sh and not report.sh?} A name without a slash is looked up only in the PATH directories, and the current directory is not one of them, so \texttt{report.sh} gives \texttt{command not found} (Figure~5.2). Keeping \texttt{.} out of PATH prevents a file planted in some directory from shadowing a real command such as \texttt{ls}. \texttt{./} is an explicit path, so no search happens.
\item \textbf{Why >\&2 and exit 1?} The error message goes to stderr, so it never mixes with the data on stdout: with \texttt{2>/dev/null} the message disappears but the exit code is still 1 (Figure~5.3). \texttt{exit 1} reports failure to the caller, so \texttt{./report.sh x.log \&\& next} does not continue and cron or other scripts can detect the error.
\end{utmenumerate}

\utmconclusions
The main lesson of this lab is that the shell, not the program, does most of the work on a command line. \texttt{echo} never saw \texttt{*.c}; it received ready file names. \texttt{ls alfa beta.txt} failed before \texttt{ls} had a chance to understand the name, and \texttt{wc} printed no file name because it never received one. Once the expansion order is clear (braces, variables and substitutions, then word splitting, then globbing, then quote removal), the output can be predicted. The only misprediction, \texttt{[a-b]*}, came from overlooking a file, not from the rules.

Redirection is just as mechanical: file descriptors are copied left to right, so \texttt{2>\&1} has to come after the redirection it copies. The control operators \texttt{;}, \texttt{\&\&} and \texttt{||} depend only on exit codes, and the same codes made the script errors visible: 127 for a missing command, 126 for a missing execute bit, 1 for the script's own error.

The one-liners answered every question about the 500-line log with combinations of \texttt{grep}, \texttt{cut}, \texttt{sort}, \texttt{uniq} and \texttt{wc}. Each result was verified twice: by the handout's self-checks (125$\times$4 = 500, the per-user failures sum to 100) and by modular arithmetic on the generator (100, 72/15, 50). The Q4 solution prints every user tied at the maximum, so it stays correct when the log is regenerated with different data. Finally, \texttt{report.sh} turned the pipelines into a reusable program with argument checking, a correct error stream and exit code, and it ran unattended under cron.
