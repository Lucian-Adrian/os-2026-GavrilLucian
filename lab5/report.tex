\utmintroduction
\textbf{Purpose of the work.} To see from the shell how Linux organizes files: the directory tree and the file types, the difference between a \emph{name} and an \emph{inode}, hard and symbolic links, how space is really allocated, how permission bits are checked, and how disks and the kernel itself appear as files.

\textbf{Environment.} Debian GNU/Linux 13, kernel 6.12, GNU coreutils 9.7, ordinary user \texttt{dev1} (UID 1000), working directory \texttt{\~{}/os-lab5} on an ext4 root filesystem (\texttt{/dev/sda2}). Every terminal figure is the real output of the commands shown in it.

\section{/bin is a link: the merged /usr}
\texttt{/bin}, \texttt{/sbin} and \texttt{/lib} are symbolic links into \texttt{/usr}, so \texttt{/bin/ls} and \texttt{/usr/bin/ls} have the same inode number, 2658541: they are one file reached by two paths (Figure~1.2). Debian merged the old ``essential'' \texttt{/bin} into \texttt{/usr/bin} because the split no longer matched how systems boot.
\shot{fig1_2_usrmerge.png}{The /usr merge: /bin, /sbin and /lib are links}

\section{Devices are files}
In \texttt{/dev}, the size column is replaced by \emph{major, minor}: the major number selects the driver and the minor number selects the device. \texttt{c} devices (\texttt{null} 1,3, \texttt{zero} 1,5, \texttt{random} 1,8, \texttt{tty} 5,0) are byte streams. \texttt{b} devices (the disk \texttt{sda} 8,0 and its partition \texttt{sda2} 8,2) are block-addressable. Writing to \texttt{/dev/null} discards the data; reading \texttt{/dev/zero} returns zero bytes (Figure~1.3).
\shot{fig1_3_dev.png}{Character and block devices in /dev}

\section{Where is the space?}
\texttt{/usr} uses 9.9~GiB and \texttt{/var/log} 150~MiB, about 66 times less (Figure~1.4). \texttt{/usr} holds the read-only installed software; \texttt{/var/log} holds only variable data, and it stays small because \texttt{journald} and \texttt{logrotate} cap and rotate the logs.
\shot{fig1_4_du.png}{Disk usage of /var/log and /usr}

\chapter{Inodes and links}

\section{A name is not the file}
\texttt{stat} shows everything the inode stores: size 6, 8 blocks of 512~B, inode 7481761, 1 link, mode 0644, owner and the four timestamps (Figure~2.1). The name \texttt{notes.txt} is not among them; it exists only as an entry (name $\rightarrow$ inode) in the directory \texttt{\~{}/os-lab5}.
\shot{fig2_1_stat.png}{The inode of notes.txt}

\section{Hard links}
\texttt{ln notes.txt hard.txt} adds a second name for the same inode: both names show 7481761 and the link count rises to 2. \texttt{rm notes.txt} calls \texttt{unlink()}, which removes one name and decrements the count to 1. The data is untouched, so \texttt{cat hard.txt} still prints \texttt{hello} (Figure~2.2). The kernel frees the inode only when the link count is 0 \emph{and} no process has the file open.
\shot{fig2_2_hardlink.png}{A hard link survives the removal of the original name}

\section{Symbolic links}
A symbolic link is a separate inode (7481762) whose content is a path. Its size is 8, the length of \texttt{hard.txt}. While the target exists, \texttt{cat soft.txt} follows it. After \texttt{rm hard.txt} the link dangles: \texttt{No such file or directory}, although \texttt{ls} and \texttt{readlink} still show the stored path (Figure~2.3).
\shot{fig2_3_symlink.png}{A symbolic link and how it dangles}

\section{Link count of a directory}
A new directory has 2 links: its name in the parent and its own \texttt{.}. Each subdirectory adds one more through its \texttt{..}, so after \texttt{mkdir d/x d/y} the count is 4. A regular file inside does not change it (Figure~2.4). In general, links of a directory = 2 + the number of subdirectories, which is how \texttt{/etc} reaches 122.
\shot{fig2_4_dirlinks.png}{Link count of a directory}

\section{Size versus allocated space}
\texttt{one.txt} contains 2 bytes (\texttt{x} and a newline) but occupies 4.0~KiB, i.e.\ 8 sectors of 512~B: ext4 allocates whole 4~KiB blocks. \texttt{truncate -s 1G big.img} only writes the size into the inode. \texttt{ls} reports 1.0~G, while \texttt{du} reports 0, because no block was allocated. Reading the file returns zeros generated on the fly (Figure~2.5). Such \emph{sparse} files are how VM disk images can be ``large'' and still cost nothing until they are written.
\shot{fig2_5_sparse.png}{Logical size against allocated blocks}

After \texttt{chmod 000} even the owner gets \texttt{Permission denied} (Figure~3.1). The kernel picks \emph{one} class: owner if the UIDs match, otherwise group, otherwise others. It checks only those bits, and the owner's bits are now 0. Ownership gives only the right to run \texttt{chmod}, which is how the file was made readable again. Only root bypasses the check.
\shot{fig3_1_modes.png}{Typical modes, and chmod 000 locking out the owner}

\section{umask}
The umask \texttt{0022} removes write permission for group and others from every new file. Files are created from 0666 and directories from 0777: $0666 \mathbin{\&} \lnot 0022 = 0644$ and $0777 \mathbin{\&} \lnot 0022 = 0755$, exactly as \texttt{new.txt} and \texttt{newdir} show. With \texttt{umask 077} the new file is \texttt{rw-------} (Figure~3.2). Files never start with \texttt{x}, because the base mode 0666 has no execute bits.
\shot{fig3_2_umask.png}{umask and the modes of new files}

\section{r and x on a directory}
A directory's content is a list of names. \texttt{r} allows reading that list; \texttt{x} allows \emph{using} the directory in a path to reach the inodes behind the names. With only \texttt{r}, \texttt{ls box} prints the name \texttt{f}, but \texttt{cat box/f} is denied. With only \texttt{x}, \texttt{ls} is denied, but \texttt{cat box/f} prints \texttt{hi} because the name is already known (Figure~3.3).
\shot{fig3_3_dir_rx.png}{Read and execute permission on a directory}

\section{setuid and the sticky bit}
\texttt{/usr/bin/passwd} is \texttt{4755}, \texttt{rwsr-xr-x}: the \texttt{s} (setuid) makes the process run with the effective UID of the owner, root. That is why an ordinary user can change their password in \texttt{/etc/shadow}, which is \texttt{rw-r-----} and owned by root. \texttt{/tmp} is \texttt{1777}, \texttt{rwxrwxrwt}: everyone may create files, but the sticky \texttt{t} allows deleting or renaming only one's own files (Figure~3.4).
\shot{fig3_4_setuid_sticky.png}{setuid on passwd and the sticky bit on /tmp}

\chapter{Disks and the kernel as files}

\section{Disks and mounts}
The machine has one 1.8~TiB disk \texttt{sda} (8:0) with six partitions. The root filesystem is \texttt{sda2}, ext4, 121~GiB, 35\% used, mounted \texttt{rw,relatime,errors=remount-ro}: on a disk error the kernel remounts it read-only instead of corrupting it further (Figure~4.1).
\shot{fig4_1_disks.png}{Disks, partitions and the root mount}

\section{/proc}
\texttt{/proc} is not on any disk: the kernel generates its files on every read. \texttt{/proc/cpuinfo} lists 12 logical processors (Intel Core i5-12400F, 6 cores $\times$ 2 threads), and \texttt{/proc/meminfo} reports 32\,707\,268~kB $\approx$ 31.2~GiB of RAM. \texttt{head -5 /proc/self/status} prints \texttt{Name: head}, because \texttt{/proc/self} is a link that the kernel resolves to the PID of \emph{whoever opens it}. For \texttt{ls} it pointed to 3259196, a different process from the shell, which is 3259107 (Figure~4.2).
\shot{fig4_2_proc.png}{CPU, memory and /proc/self}

\chapter{Stretch experiments}

\section{Magic numbers}
A gzip file starts with the bytes \texttt{1f 8b} (then \texttt{08} = deflate). \texttt{file} reads these bytes, not the name: \texttt{renamed.txt} is still recognized as gzip data (Figure~5.1). On Unix the extension is only a convention; the content determines the type.
\shot{fig5_1_magic.png}{The gzip magic number and file ignoring the extension}

\section{Setuid audit}
13 setuid programs exist in \texttt{/usr/bin} (Figure~5.2). Each one needs root for a single, narrow task: changing account data (\texttt{passwd}, \texttt{chfn}, \texttt{chsh}, \texttt{gpasswd}, \texttt{newgrp}), switching identity (\texttt{su}, \texttt{sudo}, \texttt{pkexec}), or mounting (\texttt{mount}, \texttt{umount}, \texttt{fusermount3}, \texttt{ntfs-3g}), plus the NVIDIA module loader. Because each of them runs as root, a bug in any one is a privilege escalation, so the list should be as short as possible.
\shot{fig5_2_setuid_audit.png}{Setuid programs in /usr/bin and /usr/sbin}

\section{Deleting an open file}
A 50~MiB file was opened on fd 3 and then removed. \texttt{/proc/\$\$/fd/3} still points to it, marked \texttt{(deleted)}, and \texttt{df} shows no change in used space: the name is gone, but the inode is still referenced by the open descriptor. Only after \texttt{exec 3<\&-} closes it does used space drop by $41\,239\,780 - 41\,188\,580 = 51\,200$~KiB, exactly 50~MiB (Figure~5.3). This is why deleting a large log that a running service still writes does not free disk space.
\shot{fig5_3_unlink_open.png}{Space is freed only when the last descriptor is closed}

\section{A filesystem in a file}
\texttt{mkfs.ext4} formatted a 64~MiB sparse file, and it was mounted through a loop device (\texttt{/dev/loop0}). \texttt{df -i} shows 16\,384 inodes, 12 already used by the root directory, \texttt{lost+found} and reserved inodes. \texttt{dumpe2fs} explains the number: for such a small filesystem mke2fs chooses 1~KiB blocks (65\,536 blocks) and one 256-byte inode per 4~KiB of space, $64~\text{MiB} / 4~\text{KiB} = 16\,384$. The inode count is fixed at format time, so a disk can be ``full'' of tiny files while blocks are still free (Figure~5.4).
\shot{fig5_4_loop_ext4.png}{An ext4 filesystem in a 64 MiB file, mounted through a loop device}

\utmconclusions
The central idea of the lab is the separation between \emph{names} and \emph{inodes}. A directory is only a table of (name, inode number) pairs, and all the real information (type, size, owner, mode, times, block addresses) lives in the inode. This one fact explains all the experiments. Hard links are just more names for the same inode, so data survives \texttt{rm} until the link count and the open count both reach zero (seen both with \texttt{hard.txt} and with the deleted 50~MiB file). A directory's link count is $2 +$ its subdirectories because of \texttt{.} and \texttt{..}. A symbolic link is a small separate file with a path and can dangle.

The size of a file and the space it uses are independent quantities: 2 bytes cost 4~KiB, and a 1~GiB sparse file costs nothing. Permissions are checked against exactly one class, which is why \texttt{chmod 000} locks out even the owner. On a directory, \texttt{r} and \texttt{x} are two different rights (listing the names and passing through them). setuid and the sticky bit are the controlled exceptions that make passwords and \texttt{/tmp} work safely.

Finally, ``everything is a file'' proved literal: disks are block devices with major and minor numbers, the kernel publishes its state through \texttt{/proc}, and a whole ext4 filesystem fit inside a regular file and was mounted like a disk.
