\utmintroduction
\textbf{Purpose of the work.} To repeat the Lab~5 experiments inside xv6, where the whole file system can be read in the source. The work covers how directories store names, what an inode holds, how links and unlinking work down to the line where blocks are freed, which hard limits follow from the constants in \texttt{kernel/fs.h}, and two new user programs: \texttt{mystat}, which prints an inode, and \texttt{find}, which walks a directory tree recursively.

\textbf{Environment.} Debian GNU/Linux 13, \texttt{riscv64-linux-gnu} GCC 14, QEMU 10.0. xv6 is the current upstream \texttt{mit-pdos/xv6-riscv} with \texttt{user/mystat.c} and \texttt{user/find.c} added to \texttt{UPROGS} (together with \texttt{sleep} and \texttt{args} from Lab~4). Each QEMU session started from a freshly built \texttt{fs.img}. Every terminal figure is the real output of the commands shown in it.

\chapter{Directories and file types}

\section{Types, the root inode and the directory entry}
xv6 knows three file types, defined in \texttt{kernel/stat.h}: \texttt{T\_DIR} = 1, \texttt{T\_FILE} = 2, \texttt{T\_DEVICE} = 3. The root directory is inode \texttt{ROOTINO} = 1. A directory is a regular array of \texttt{struct dirent}: a 2-byte inode number \texttt{inum} and a 14-byte name \texttt{name[DIRSIZ]}, 16 bytes per entry (Figure~1.1).
\shot{fig1_1_types_src.png}{File types, ROOTINO and struct dirent in the source}

\section{ls in xv6}
xv6 \texttt{ls} prints name, type, inode and size for each entry (Figure~1.2). In \texttt{/}, both \texttt{.} and \texttt{..} are inode 1: the root is its own parent. The programs are type 2 with inodes 3, 4, \ldots, assigned in \texttt{UPROGS} order by \texttt{mkfs}, and \texttt{console} is type 3, a device with size 0. A new directory \texttt{a} has size 32: exactly two entries, \texttt{.} (its own inode) and \texttt{..} (inode 1), $2 \times 16 = 32$ bytes.
\shot{fig1_2_ls.png}{ls of the root directory and of a new directory}

\chapter{mystat and the life of a link}

\section{user/mystat.c}
\texttt{mystat} calls \texttt{stat()} for every argument and prints the type as a word, the inode number, the link count and the size. A path that cannot be resolved is reported on stderr, and the program continues with the remaining arguments (Figure~2.1).
\shot{fig2_1_mystat_c.png}{The source of user/mystat.c}

\section{Links and unlinking}
\texttt{ln README r2} creates a second directory entry for inode 2: both names show \texttt{links 2} and the same size, 2441. \texttt{rm README} removes only the entry. The count falls to 1, and \texttt{r2} still holds the full text: \texttt{cat r2 | wc} prints \texttt{48 336 2441} (Figure~2.2).

Two details differ from Linux. The root \texttt{.} shows \texttt{links 2} and the new directory \texttt{a} shows \texttt{links 1}. xv6 does not count a directory's own \texttt{.} entry, so a new directory has one link, its name in the parent. Every subdirectory then adds one to its parent through \texttt{..}, which is why \texttt{/} went from 1 to 2 when \texttt{a} was created.
\shot{fig2_2_mystat_links.png}{mystat, a hard link and unlink}

\section{Where the blocks are really freed}
\texttt{sys\_unlink()} in \texttt{kernel/sysfile.c} clears the directory entry and does \texttt{ip->nlink--} (line 244). It does not free any data. Line 239 is the extra decrement for removing a directory (its \texttt{..} pointed to the parent), and line 178 rolls back a failed \texttt{link()}. Data is freed only in \texttt{iput()} in \texttt{kernel/fs.c}. When the last in-memory reference is dropped (\texttt{ref == 1}) and the on-disk count is 0 (\texttt{nlink == 0}), \texttt{itrunc()} returns every direct and indirect block to the free bitmap (lines 357--366, Figure~2.3). So a file that is deleted while a process still has it open stays readable until the process closes it, which is the same rule observed on ext4 in Lab~5.
\shot{fig2_3_unlink_src.png}{nlink-- in sysfile.c and the freeing condition in iput()}

\chapter{Limits and disk layout}

\section{The constants and the on-disk inode}
\shot{fig3_1_constants.png}{Constants in fs.h and param.h, and struct dinode}
The on-disk inode \texttt{struct dinode} has only \texttt{type}, \texttt{major}, \texttt{minor}, \texttt{nlink}, \texttt{size} and 13 block addresses: $4 \times 2 + 4 + 13 \times 4 = 64$ bytes. Compared with ext4 it lacks owner, permission bits, timestamps and symbolic links, so xv6 has no \texttt{chmod}, no users and no \texttt{ls -l} times.

\section{Names longer than 14 characters}
\texttt{mkdir averyveryverylongname} succeeds, but \texttt{ls} shows \texttt{averyveryveryl}, the first 14 characters (Figure~3.2). The same happens with files: \texttt{echo hi > abcdefghijklmnopq} creates an entry named \texttt{abcdefghijklmn}, and \texttt{cat abcdefghijklmn} prints \texttt{hi}. The long name itself also keeps working (\texttt{mystat abcdefghijklmnopq} finds inode 30). \texttt{namecmp()} compares only \texttt{DIRSIZ} bytes, so every name that shares the first 14 characters refers to the same file. Linux would reject such a name with \texttt{ENAMETOOLONG} instead of truncating it silently.
\shot{fig3_2_truncation.png}{Names truncated to 14 characters}

\chapter{user/find.c}

\section{How it works}
\texttt{find <dir> <name> [-n]} opens the directory and checks with \texttt{fstat()} that it really is one. It then reads it one \texttt{struct dirent} at a time and skips free slots (\texttt{inum == 0}). The 14-byte name is copied into a buffer one byte longer so that it can be terminated even when it is exactly 14 characters long. It skips \texttt{.} and \texttt{..}; otherwise the recursion would loop forever, going down into itself or back up into its parent. For each entry it builds \texttt{path/name}, prints it if the name matches (with the inode number when \texttt{-n} is given), and recurses into subdirectories. Every opened directory is closed before returning, so deep trees do not exhaust the 16 file descriptors a process has (\texttt{NOFILE}). It also refuses paths that would overflow its 512-byte buffer (Figure~4.1).
\shot{fig4_1_find_c.png}{The search function of user/find.c}
\shot{fig4_0_main.png}{Argument handling in main()}

\section{Testing find}
In the tree \texttt{/r2}, \texttt{/a/r2} and \texttt{/a/b/r2}, \texttt{find . r2} finds all three, and \texttt{find a b} finds the directory \texttt{a/b} (Figure~4.2). With \texttt{-n}, the three files named \texttt{r2} have three different inodes (32, 33, 2): the same name does not mean the same file. In the opposite case, after \texttt{ln cat c2}, \texttt{find . c2 -n} reports inode 3, and \texttt{mystat cat c2} confirms that \texttt{cat} and \texttt{c2} are one inode with 2 links. A missing argument prints the usage line, and a missing directory prints \texttt{find: cannot open nosuch}.

\utmconclusions
The xv6 file system made the Lab~5 rules visible in the source. A directory is literally an array of 16-byte \texttt{(inum, name)} records, and \texttt{ls}, \texttt{mystat} and \texttt{find} only read those records and call \texttt{stat()}. The life of a file is controlled by two counters. \texttt{nlink} counts names on disk and is decremented by \texttt{sys\_unlink()}; \texttt{ref} counts in-memory users. Blocks are freed by \texttt{itrunc()} in \texttt{iput()} only when both reach zero, which is why \texttt{r2} kept the full 2441 bytes after \texttt{README} was removed.

The limits follow directly from a few constants: 1~KiB blocks, 12 direct pointers plus one indirect block give a maximum file of 268~KiB, \texttt{DIRSIZ} = 14 silently truncates longer names, and the 2000-block disk spends 47 blocks on boot, superblock, log, inodes and bitmap. The comparison with Lab~5 shows what a production file system adds on top of the same design: owners and permissions, timestamps, symbolic links, larger and multi-level indirect blocks (extents in ext4), and errors instead of silent truncation. The \texttt{find} program needed no kernel support at all: recursion over \texttt{open}, \texttt{read} and \texttt{stat} was enough, as long as it skips \texttt{.} and \texttt{..} and closes every descriptor.
